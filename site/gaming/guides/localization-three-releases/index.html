Что изменилось в двух релизах

В первой версии 23 текстовые строки, во второй и третьей — по 25. Каждый релиз содержит английский оригинал и актуализированный русский JSON. «До» означает сравнение нового оригинала со старым переводом; «после» — с обновлённым.

ПереходСтрокНовые / изменённые / удалённыеДо: ошибки / предупрежденияПосле: ошибки / предупреждения
v1 → v223 → 253 / 4 / 14 / 10 / 0
v2 → v325 → 252 / 4 / 22 / 20 / 0

Для ручной проверки появляется 7 новых и изменённых строк в первом переходе и 6 во втором. Неизменившиеся строки — 18 и 19 соответственно. Удалённые пути учитываются отдельно. После актуализации структурных расхождений нет, но исходные изменения остаются в списке: исправленный JSON не является автоматической приёмкой смысла.

Подстановка совпала — действие изменилось

v1: "Hold {key} to inspect"
v2: "Press {key} to inspect"

Было:  «Удерживайте {key}, чтобы осмотреть»
Стало: «Нажмите {key}, чтобы осмотреть»

Идентификатор и подстановка прежние. Обычная структурная проверка может пропустить устаревшее указание действия. В списке изменений эта строка видна; решение о формулировке записано по учебному контексту.

Другой релиз — другой термин

v2: "Coins: %d"   → «Монеты: %d»
v3: "Credits: %d" → «Кредиты: %d»

Тип %d не менялся. Во втором переходе валюту переименовали, подпись завершения задания стала подписью контракта, а кнопка продолжения стала загрузкой последнего сохранения. Даже нулевое число ошибок подстановок не подтверждает актуальность этих формулировок.

Новая подстановка требует изменения перевода

v1: "Overwrite saved game?"
v2: "Overwrite slot {slot}?"

Было:  «Перезаписать сохранение?»
Стало: «Перезаписать ячейку {slot}?»

Здесь меняется и смысл, и структура. Старому переводу не хватает {slot}; отчёт первого перехода показывает отдельную ошибку. Перед выпуском нужно проверить подстановку с реальным значением выбранной ячейки.

Как повторить проверку

  1. Скачайте и распакуйте набор. Файлы UTF-8 JSON лежат в v1, v2 и v3.
  2. Откройте проверщик и выберите «Локализацию после обновления».
  3. Для первого перехода загрузите v1/en.json, v2/en.json и v1/ru.json. Нажмите «Проверить»: 3 новых, 4 изменённых, 1 удалённая строка; 4 ошибки и 1 предупреждение.
  4. Замените только перевод на v2/ru.json и повторите. Ошибок и предупреждений нет; список изменений оригинала сохранён.
  5. Для второго перехода возьмите v2/en.json, v3/en.json и v2/ru.json, затем повторите с v3/ru.json.
  6. Сопоставьте результат с reports, а решения по контексту — с decisions.json. В архиве есть инструкция и скрипт воспроизведения для Node.js.

Удалённые ключи исключены из перевода осознанно для этого вымышленного сценария. В реальной игре они могут оставаться нужны для старых сохранений, модов или другого экрана. Автоматически удалять их по одному отчёту нельзя.

Что измерено, а что ещё нужно проверить

Один запуск чтения шести небольших JSON, трёх структурных проверок и четырёх сравнений с контрольными проверками занял 38.196 мс в Node v24.19.0 на win32 / x64. Это измерение автоматической части на конкретной машине. В него не входят подготовка формулировок, контекстная проверка, создание архива, браузерная проверка и игровой запуск. Использовать эти миллисекунды как срок перевода нельзя.

Для настоящего проекта после файлового этапа нужны утверждение смысла, проверка кириллицы, длины подписей, реальных значений подстановок и затронутых экранов на указанной версии. У этого набора нет движка, экранов и сохранений — игровую совместимость он не доказывает.
